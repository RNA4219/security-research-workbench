# 実モデルを使った診断フィードバックの証跡

対象は、この評価専用に作った小さなGitリポジトリと分離DBです。テスト主体による判断は実利用者の承認ではありません。モデル候補と固定ルールの指摘が重なるため、発見範囲の証明には使いません。

| 実行 | 結果 | 確認できたこと |
|---|---|---|
| live-20261005-01 | 起動設定で失敗。モデル呼出し0回 | 別のビルド出力先を指定したが、評価処理が標準のdist内に限定していたため拒否。失敗のartifactを保存 |
| live-20261005-02 | 判断再利用の条件を満たさず失敗。モデル呼出し2回 | 初回・同条件の再診断はともに完了し、各1件のモデル候補を保持。ただし説明文の変化を根拠変更と判定し、確認待ちは1件のまま |
| [live-20261005-03](live-20261005-03/artifact.json) | 明示的にコード範囲を選ぶ別条件で合格。実モデル呼出し3回 | 初回→同条件→仕様変更で、生のモデル候補は各1件、確認待ちは1→0→1件。3回とも診断・モデル工程が完了 |

02ではコード箇所、原文、種類、重大度、仕様参照が同じでも、AIのタイトル・理由・修正案が言い換わりました。既存の厳密な比較では `evidence_changed` として再確認になります。これを確認作業の削減成功とは数えません。仕様変更を試す3回目には進んでいません。

JSONは元の `.cache/diagnostic-feedback-live-20261005-01/` と `-02/` からバイト列を変えずに保存しました。02にはモデルの生の入出力、fixtureのsourceとcommit、実際に使ったビルド・評価スクリプト・package-lockの内容とハッシュがあります。SQLite DBとGit作業ディレクトリは、元のローカル評価フォルダーに保持しています。

03も同様に元の `.cache/diagnostic-feedback-live-20261005-03/` のJSONをバイト単位で保存しています。[モデルと実行条件](live-20261005-03/runtime-configuration.json)には、再計算したモデルファイルのSHA-256と実行PID、参照した設定を記録しました。[生の入出力](live-20261005-03/raw-invocations.json)と[実行コード](live-20261005-03/runtime-source-snapshot.json)も確認できます。artifact SHA-256は `b4307d239cabe71ef95b5ca74c65b01328541f8e4c29e54ef7edd654ebf85a50` です。

03はテスト主体が `source_scope` を明示選択した評価です。同じ固定版・コード箇所・原文・種類・重大度・仕様参照等の範囲に説明文の変更を含める設定で、意味が同一だとAIが保証するものではありません。既定の厳密比較を使った02の失敗を成功に書き換えていません。仕様変更後は旧判断IDがモデル入力から除外され、確認待ちへ戻りました。1つのfixtureの確認待ち件数を測った結果であり、モデル精度・実人時間・実製品全般の改善率は未測定です。
