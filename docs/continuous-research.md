# 製品知識・人の判断・修正確認を管理する

本書は製品の知識・判断・修正を管理する画面とAPIの説明。ホームからの登録・コード診断・更新後の比較は[特定製品の継続診断](product-diagnostics.md)を参照する。診断結果からこの案件画面へ進むと、固定コミットとコードの根拠を使って影響や修正を検討できる。モデルへの照会だけで診断や修正完了を自動確定しない。

この機能はローカル版の「調査・判断・修正」で使う。公開サイトは、公開GitHub URLからの採用前調査の入口を提供する。

例えば、候補ライブラリの既知問題を見つけたとき、「自分たちが使う機能にも関係するのか」「前回の見送り理由は今も有効か」「更新したら確認が終わったと言えるか」を扱う。URLの調査結果に、製品仕様、利用条件、判断の根拠を足していく。

## 一度試す手順

1. 製品診断の結果から「知識・判断・修正へ」または指摘の「案件の判定・修正記録を開く」を押す。製品専用の案件に仕様・診断根拠が保存される。補助機能のURL調査から「この結果から採用判断を続ける」でも、対象コミットと原文を引き継いだ別の案件を作れる。
2. 「対象と許可範囲」で、目的、対象版、管理範囲を確認する。初期設定は公開情報の確認と手動受渡し。通常機能試験や外部モデルは、使う前に許可範囲を設定する。
3. 自分たちの利用条件を資料に追加する。例：「ログは30日保存する」「管理APIは管理者だけが使う」。資料の公開区分を選び、原文を引用して知識案を作る。
4. 判断者と理由を入力して知識案を承認する。以降の照会は、この案件の目的に合う承認済み・現行版だけを使う。未承認案や失効した資料は使わない。
5. 手動受渡しで質問を実行する。保存されたプロンプトと、その応答形式を使う。回答は提案として保存され、人の判断や修正完了を自動確定しない。
6. 指摘に「対応必要」「誤検出」等の人の判断を記録する。同じ条件の既知事項を期限付きで抑止できる。根拠・対象版・基準が変わったら再確認する。
7. 対応が必要なら、担当者、修正計画、作業の参照、修正コミット、確認方法と証跡をつなぐ。対象版に一致する有効な確認証跡と、人の完了判断が必要。

問い合わせ、判断、修正で得た内容は知識の更新案にできる。案を作った時点では旧版が有効なまま。承認後に新しい版へ切り替わり、次の照会に反映される。却下した案と理由も残る。

## 保存と再開

案件には独立したrevisionを持たせ、古い画面による上書きを拒否する。各revisionの原文、知識、基準、判断はSQLiteの履歴で保持する。

実行はコンテキストの固定、モデルへの受渡し、応答照合の工程に分かれる。工程ごとに入力条件、知識・基準の版、設定、試行回数、中間成果物を保存する。同じ条件なら完了した工程を残して再開し、条件が変われば旧実行を保持した別の実行になる。再起動しても自動では処理を再開しない。

時間・費用・工程数・同時実行数・再試行回数の上限を開始前に設定する。接続先を勝手に切り替えない。資料本文やモデルの秘密鍵をアクセスログへ出さない。

## モデル接続

設定なしで手動受渡しが使える。実モデルを接続するときは、起動するプロセスの環境変数を設定する。接続先は画面から任意指定できない。次の設定に加え、案件の許可providerで送信先を選ぶ必要がある。

| 接続 | 設定 |
|---|---|
| ローカル | `WORKFLOW_LOCAL_URL`、`WORKFLOW_LOCAL_MODEL`。URLはループバックのみ |
| 許可した外部接続 | `WORKFLOW_CLOUD_URL`、`WORKFLOW_CLOUD_MODEL`、`WORKFLOW_CLOUD_ALLOWED_HOSTS`、`WORKFLOW_CLOUD_API_KEY`。HTTPSかつ明示したホストのみ |
| 費用の見積り | `WORKFLOW_{LOCAL,CLOUD}_INPUT_USD_PER_MILLION_TOKENS`、`WORKFLOW_{LOCAL,CLOUD}_OUTPUT_USD_PER_MILLION_TOKENS` |
| 出力と設定版 | `WORKFLOW_{LOCAL,CLOUD}_MAX_OUTPUT_TOKENS`、`WORKFLOW_{LOCAL,CLOUD}_CONFIG_VERSION` |

APIはOpenAI互換のChat Completions形式を使う。URLはサーバーのルートまたは`/v1`までを指定する。リダイレクトを追わない。外部接続には質問と知識の両方が公開区分であることが必要。費用見積りを設定できない外部接続は自動実行を始めない。手動受渡しの外部サービス費用はアプリでは把握できず、未測定として扱う。

実モデルの応答品質・精度は、アダプターの契約テストと別の検証対象。モデルを変えた効果を比べる場合は、同じ対象版、質問、知識、基準、正解集合を使い、見落とし・誤提示・重複・人の確認時間・実行時間・費用を分けて読む。未測定を0として扱わない。

実行時間は工程が動作した累積時間で、手動応答を待った時間は含めない。人の確認時間は別の入力値として比較する。手動受渡しの待ち時間が短いだけで、業務全体が速くなったとは判断できない。

## APIと保存先

基底は`/api/projects/:id/workflow`。既存APIと同じHost/Originと`X-Workbench: 1`の制約を受ける。

| 操作 | エンドポイント |
|---|---|
| 案件読込 | `GET` 基底 |
| 範囲・資料・知識・基準・判断・修正更新 | `POST /commands`、`{revision, command}`。形式は`src/shared/workflow.ts` |
| 調査結果取込 | `POST /import-research`、`{revision, researchId}` |
| 参照候補の取得 | `POST /context`、`{question, providerKind}` |
| 変更履歴 | `GET /history`、`GET /history/:revision` |
| 実行と接続の一覧 | `GET /runs` |
| 実行開始・状態 | `POST /runs`、`GET /runs/:runId`。形式は`src/shared/workflow-run.ts` |
| 停止・再開 | `POST /runs/:runId/stop`、`POST /runs/:runId/resume`、本文`{}` |
| 手動応答 | `POST /runs/:runId/response`、`{response}` |
| 条件を固定した比較 | `POST /compare`。比較条件と結果は案件のartifactへ保存 |
| 調査結果から案件作成 | `POST /api/research/:id/adopt`、本文`{}` |

既存DBに`workflows`、`workflow_history`、`workflow_runs`、`research_cases`を追加する。既存プロジェクトを変更せず、初めて開いた時に案件状態を初期化する。`.data/`内の資料、判断、実行記録、設定の秘密値はGitや公開サイトへ配置しない。

通常機能・回帰試験の実行は利用者の管理環境で行い、本アプリへ方法と証跡を記録する。任意コマンド実行、攻撃再現、独自の脆弱性スキャナー、複数ユーザーの認証は提供しない。
