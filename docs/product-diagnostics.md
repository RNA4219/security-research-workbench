# 特定製品の継続診断

ローカル版で、登録した製品のGitコミットを固定して静的診断し、次の版と比較します。公開サイトは架空データによる診断モックと、OSSのURL調査を提供します。実際の製品診断にはローカル版を使ってください。

## 始め方

1. `npm ci`、`npm run build`、`npm start`でローカル版を起動する。
2. ホームの製品登録で、設定済みリポジトリ、対象のブランチまたはコミット、製品仕様を入力する。
3. 診断を開始する。ブランチ名は開始時にコミットへ固定され、作業ツリーの未コミット変更は対象にしない。
4. 指摘候補、コード位置、解析した範囲、未診断範囲を確認する。候補から製品知識と人の判断の画面へ進む。
5. 更新後の版を指定して再診断する。新規・継続・要確認・今回未検出を読み分ける。
6. 修正版の診断と通常の回帰試験の証跡を確認してから、人が修正完了を判断する。今回未検出という表示だけでは自動完了しない。

## 対象リポジトリを設定する

サーバーを動かす利用者が、環境変数 `WORKBENCH_DIAGNOSTIC_REPOSITORIES` にIDとローカルGitパスのJSONを設定する。画面から任意のホストパスや外部の診断対象を指定する機能はない。既定の登録対象については設定一覧を確認する。

```powershell
$env:WORKBENCH_DIAGNOSTIC_REPOSITORIES = '{"my-product":"C:/work/my-product"}'
npm start
```

パスはこの例を実際の製品のパスへ置き換える。設定を変更した場合はサーバーを再起動する。対象製品のソース・案件・判断・実行履歴はローカルDBで扱い、公開サイトやGitへ保存しない。RSI-pentestは登録・読取・連携の対象外。

## 診断の範囲

コードは実行せず、[Babel parser](https://babeljs.io/docs/babel-parser)でJavaScript/TypeScriptの構文を読む。初期の解析対象はTLS検証の無効化や暗号関連の限定した設定・呼出し。コード全体の安全性、認可設計、実行時の到達可能性を網羅して判定するものではない。コメントや単なる文字列をコードの呼出しとして扱わない。

依存関係はnpm lock v2/v3を扱い、既存の[OSV照合](https://google.github.io/osv.dev/post-v1-querybatch/)を利用する。ネット照合は製品設定で明示的に許可した場合だけ行い、送る内容は公開npmレジストリに対応する依存名と版。コードや製品仕様はこの処理で送信しない。未許可・取得失敗・形式未対応を未照合として残す。

TLS設定の解釈は[Node.js TLS](https://nodejs.org/api/tls.html#tlsconnectoptions-callback)、暗号アルゴリズムの選択は[Node.js Crypto](https://nodejs.org/api/crypto.html#support-for-weak-or-compromised-algorithms)を根拠とする。静的な指摘は候補であり、利用目的や製品仕様に照らした影響の判定は別工程。

## 製品知識と判断

各製品には独立した継続案件を関連付ける。製品仕様・診断根拠・知識の承認、人の判定、修正の追跡には[既存の継続案件](continuous-research.md)を使う。静的ルールは自然言語の知識によって自動変更されない。コードで得た候補を、承認済み製品知識を参照する照会で評価する。

ルールや製品知識の版は実行記録に残します。条件が変わった過去判断を無条件に流用しません。案件画面での質問は手動受渡しが既定です。製品のAIレビューは、以下の設定で別途有効にします。実モデルの精度や業務効果は、画面・APIのテストとは分けて評価します。

## AIレビューを使う

固定ルールによる検査に、ローカルモデルのコードレビューを追加できます。モデルは、製品仕様・承認済みの知識・条件が一致する過去の判断を参照します。指摘には対象コミットのコード位置と原文が必要で、存在しない行や未知の参照IDを含む応答は失敗として扱います。

OpenAI互換のChat Completions APIを提供するモデルを、同じPCで先に起動してください。次はPowerShellでの設定例です。モデル名とポートは、起動したモデルの設定に合わせます。

```powershell
$env:WORKFLOW_LOCAL_URL = 'http://127.0.0.1:8081'
$env:WORKFLOW_LOCAL_MODEL = '使用するモデル名'
$env:WORKFLOW_LOCAL_MAX_OUTPUT_TOKENS = '2048'
$env:WORKFLOW_LOCAL_CONFIG_VERSION = 'local-v1'
npm start
```

対応するllama.cppモデルで推論文の出力を無効にする場合は、起動前に `$env:WORKFLOW_LOCAL_DISABLE_THINKING = 'true'` も設定します。JSON出力を指定する場合は `$env:WORKFLOW_LOCAL_JSON_MODE = 'true'` を追加します。[llama.cppのAPI仕様](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md#post-v1chatcompletions-openai-compatible-chat-completions-api)が対応する形式です。モデル・設定・コンテキスト長を変えたら、設定版も変えてください。

1. 製品の登録または設定で、AIレビューのモデルを選びます。
2. 「ローカルモデルでコードをレビューする」を有効にして保存します。
3. 診断を開始します。「AIレビューの記録」で、処理の完了・失敗・未レビューを確認します。
4. 指摘のコード位置と仕様を照合し、人が対応方針を判断します。
5. 「参照した知識と入力の記録」で、知識の版と入力ハッシュを確認します。

コードと製品資料を渡す先は、同じPCのモデルだけです。製品の自動AIレビューは外部モデルに対応していません。ファイル数・入力サイズ・工程数・出力長には上限があり、処理できなかった範囲を表示します。再開できるのは条件が同じ実行で、保存済みの完了工程を再利用します。

**モデルがコードを読めたことと、問題を正しく見つけたことは別です。** 指摘ゼロやレビュー完了を安全性の証明にはしません。現在の確認結果と未達事項は[実モデルの検証記録](testing/2026-10-05-model-review.md)を参照してください。

## 更新時・定期実行・CI

通常は画面から次の対象版を指定して実行する。定期実行は既定で無効であり、製品の設定で有効化したときだけ、起動中のサーバーが処理する。PC停止中の処理や外部からの着信を提供する常駐クラウドサービスではない。

途中結果はローカルDBへ保存する。明示再開では固定コミットのソース取得結果と、完了した解析工程を再利用し、一部未診断・未完了の工程を再試行する。条件・許可範囲・知識・解析器の版が変わった場合は新しい実行を要求する。サーバー再起動によって診断を勝手に再開しない。保存するソース本文はAPI応答へ出さず、画面には指摘箇所の抜粋とファイル情報を返す。

同じホストのCI/端末からは次のCLIも使える。製品IDは画面または`GET /api/products`で確認する。CI要求には一意なIDを指定し、同じ要求の再送では同じ実行を参照する。

```sh
node scripts/diagnose-product.mjs --product <製品ID> --request-id <CI実行ID> --ref <対象コミット>
```

接続先は既定で`http://127.0.0.1:4317`。必要なら`--base-url`で同じホストの別ポートを指定する。終了値0は定義した範囲の処理完了、2は一部未診断、1は失敗等。0でも「安全」「指摘なし」「修正完了」を意味しない。製品のコードからコマンドを取り出して自動実行することはない。

## データと検証

データは既存の`.data/workbench.db`へ追加のテーブルとして保存する。旧プロジェクトは保持する。診断にはコミット、解析器版、仕様・知識の版、対象範囲、原文に基づく指摘を関連付ける。

[受入計画](manual-bb/product-diagnostics-plan.md)は同一製品の初回、更新、修正の3版を対象にする。[実行記録](testing/2026-10-04-product-diagnostics.md)で、実解析、固定応答の契約試験、ブラウザー操作、実業務の効果測定を区別する。これは限定された静的診断の継続運用であり、Logosと同等の検出力を実証したものではない。
