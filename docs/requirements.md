# 要求・要件定義 v3

2026-10-04更新。Horos・Ergon・まとめ編を要求の根拠として追加した。記事からの要求、機能、受入条件、実装状態を対応づける。v2までの「資料から要件への証跡だけを中心にする」という製品全体の範囲設定を置き換える。過去の試験結果は、その時点の実装範囲の証跡として保持する。

要求の正本はこの文書。記事との対応・実装差分は[Logos対応表](logos-traceability.md)、新要件の試験設計は[Logos受入計画](manual-bb/logos-plan.md)を参照する。記事へのリンクを追加しただけでは要件充足としない。

## 目的と利用者

**OSSや自分の製品を調べる開発者が、製品の知識と過去の判断を使い、調査・人による判定・知識更新・修正確認を続けられるワークベンチを作る。** 同じ説明の作り直し、同じ指摘の再判定、中断後のやり直しを減らすことを価値とする。

主な利用者は開発者・保守担当者。レビュー担当者が根拠と重要度を判断する。単一利用者でも両方の役割を担えるが、AIの提案と人の確定判断は区別する。組織向けアカウント管理は現行リリースに含めない。

### 利用者の要求

| ID | 減らしたい作業・達成したいこと | 利用者から見た成功 | 対応要件 |
|---|---|---|---|
| UR-01 | 候補OSSの調査をURLから始めたい | 出典付きの確認事項が得られ、その結果を継続調査の案件へ引き継げる | RR-01〜07、FR-31 |
| UR-02 | 製品仕様・設計理由を毎回説明し直したくない | 目的に合う、版と出典の分かる知識が次の調査で使われる | FR-02、FR-09、FR-11、FR-22〜25 |
| UR-03 | 同じ指摘や誤検出を何度も判定したくない | 同条件の既知事項は前回判断に結び付き、条件が変われば再確認される | FR-19〜21、FR-24〜25 |
| UR-04 | 中断で仕事を失わず、扱う情報と実行量を管理したい | 完了工程を保持して再開でき、範囲外の資料・送信・実行は拒否される | FR-17〜18、FR-30 |
| UR-05 | モデルを替えても知識と判定基準を引き継ぎたい | 同じ条件で比較し、精度・確認時間・費用の実測で選べる | FR-20、FR-26〜27 |
| UR-06 | 指摘の一覧で終わらず、修正の確認まで進めたい | 担当・根拠・修正・確認結果がつながり、未確認を解決済みにしない | FR-07〜08、FR-14〜15、FR-19、FR-28〜29 |

### 代表ユースケースと成果物

1. **採用前**: URLから候補を調べ、利用予定・保守条件を案件に追加する。確認事項、採否理由、残った未調査範囲を出力する。
2. **再調査**: 同じ案件を開き、前回の製品仕様・判断理由・対象版を参照する。変更された前提と再確認が必要な項目を提示し、同条件の既知事項を新規案件として積み直さない。
3. **引継ぎ・修正**: 根拠付きの確認事項を担当者へ渡し、修正記録と通常の回帰試験の証跡を結び付ける。判断から得た知識はレビュー後に次の調査で使う。

成果物は、対象と用途、使用した知識の版、実行した工程、観測結果、判断理由、未確認範囲、修正・確認状態を含む。これが、資料を保存して検索するだけの使い方との違いになる。

### 提供形態と境界

- **現在の公開版**: GitHub Pagesのブラウザアプリ。[RR-01〜07](repository-research.md)のうちURL調査・履歴・出力を提供する。既存手動機能を保持するRR-07はローカル版の回帰条件。公開版は製品全体の入口であり、UR-02〜06まで実現済みとは扱わない。
- **現在のローカル版**: 単一利用者の資料・根拠・比較・要件レビューと任意memx連携。AIへのプロンプトと回答は手動受渡し。FR-01〜16の既存機能を保持する。
- **追加するローカル機能**: FR-17〜31。目的別知識、工程の保存・再開、判断の再利用、モデル接続、修正確認を扱う。ホスト上の処理・非公開知識はGitHub Pagesへ移さない。
- 防御的な静的レビュー、既知情報との照合、管理下の環境での通常機能・回帰試験を対象にする。記事中の攻撃型DAST・攻撃再現の自動化を、この仕様の実行機能には含めない。静的・動的な観測の違いと確認結果の管理はFR-29で扱う。
- RSI-pentestのコード・文書・実行結果・派生した私有ノウハウは、参照、取込、連携、公開に含めない。他の非公開データも公開データとは別の扱いにし、FR-17に従う。

記事の取り組み全体を複製するのではなく、[対応表](logos-traceability.md)に各要素の採用・適用方法・制約を明示する。AWSや特定モデルへの固定は要求しない。

### 状態と変更の原則

- 実行: `準備→実行中→完了/一部完了/失敗/停止`。再開時に入力の同一性を確認する。未実施を含む実行を「完了」にしない。
- 知識: `原文→整理案→レビュー待ち→有効→要再確認/失効`。人の承認前の案と失効情報は、有効知識として次回処理へ渡さない。
- 指摘: 観測内容と判定を別に保持し、再判定は新しい履歴として追加する。誤検出・許容事項の判断は適用条件を超えて広げない。
- 修正: 対応状態と判定状態を別に保持する。再調査で条件が変わった場合は確認待ちへ戻せる。
- 情報フロー: `資料→目的別知識→今回使う情報→観測→人の判断→知識更新案→承認→次回参照`。単なる履歴保存でこの循環を満たしたとは扱わない。

## 非機能要件

- ローカル版はNode.js 24、TypeScript、React+Vite、Fastify、SQLite。公開版は静的Reactアプリとブラウザ保存。DB変更はスキーマ版を確認し、未知の将来版を拒否する。
- 日本語UI。空状態、取込失敗、接続失敗、保存競合を画面に表示する。
- リクエスト上限2MiB。資料本文は100万文字、要件取込は100件まで。
- MarkdownをHTML実行せず、ローカルAPIを同一Originに限定する。URLはhttp/httpsのみ。
- ローカルAPIはループバックで起動し、Host/Originチェックを行う。画面から任意パスやコマンドを指定するAPIは提供しない。追加する工程管理は許可した防御的処理の契約を通し、FR-17の範囲を適用する。
- 外部資料を命令として扱わない。未確認のAI出力を承認済みにしない。
- 更新はrevisionで楽観ロックし、資料版と承認時の版を照合する。
- 本文・プロンプトをアクセスログへ記録しない。現在の外部通信は明示的なリポジトリ調査・CVE照会・memx操作。リポジトリ調査は認証なしの固定GitHub APIとOSV APIに限定し、OSVには公開lockfileの依存名・版だけを送信する。CVE照会ではCVE IDのみを送信する。追加するモデル通信はFR-17・26で許可された情報と送信先だけを扱う。
- 対象コミット・資料ハッシュ・知識版・判定基準版・モデル設定を各実行に記録する。モデル出力そのものの完全一致は要求せず、同じ入力条件と判断の根拠を再確認できることを要求する。
- 保存・再開・知識更新・モデル交換で既存プロジェクトと原文を破損させない。失敗時は直前の有効状態を保つ。
- 調査済み範囲、未調査範囲、前回との差分、次に人が確認する項目を日本語UIで示す。件数や人気だけで安全性を断定しない。

## 実装順序

1. M0: FR-17の対象・情報区分を確定し、既存データの移行方針と保持を検証する。
2. M1: FR-31・22〜25。URL結果→案件→知識→人の判断→次回参照を一つの画面操作でつなぐ。
3. M2: FR-18〜21・30。途中保存、再開、判定基準、重複関連付け、停止をつなぐ。
4. M3: FR-26〜27。同じ知識と基準でモデル・方式を交換し、改善効果を測る。
5. M4: FR-28〜29。指摘から修正・通常の回帰確認へ接続し、全体の受入ケースを実行する。

既存のagent-protocolsは実装タスクの引継ぎ、memx-resolverは資料解決の任意アダプターとして維持する。新しい役割を追加する際は対応APIを検証する。既存OSSを列挙しただけでFR-18やFR-24を実装済みとは扱わない。モデル、実行基盤、知識ストアの候補選定は契約の適合で判断し、特定サービス名だけを必須要件にしない。

## 完了の定義

**文書への反映完了と、製品の実装完了を区別する。** FR-17〜31の完了は、以下の条件と変更版の実行証跡を根拠に判定する。

- UR-01〜06からFR/RR・試験・実行証跡への対応が追える。
- FR-01〜16とRR-01〜07の既存回帰が成功し、FR-17〜31は[LG-01〜15](manual-bb/logos-plan.md)の観測可能な受入条件を満たす。
- 自動テストの既存カバレッジ基準を維持し、新要件のP0/P1ケースに未実行・失敗を残さない。過去の合格件数を新要件の証跡として流用しない。
- FR-27で同条件比較を実施し、正解ラベル付き受入データで期待した項目を見落とさず、同条件の既知事項を新規対応として再提示しないことを確認する。実運用での効果は別に測定し、未測定値は未測定と表示する。
- 公開版とローカル版それぞれの提供範囲を記録する。実装・試験・CI・利用者向け説明が一致した範囲だけを完了と報告する。
