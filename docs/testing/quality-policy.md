# ローカル機能検証ポリシー v1

ユーザーの「テストを拡充し、最後まで実施する」という依頼に基づく技術検証。公開・デプロイに関する人の承認を代行しない。

- RanDによる現行要件15件の抽出・監査を原文ハッシュで照合する。
- Code-to-gateの静的指摘を残さず、readiness passedを必要とする。抑制やwaiverを使わない。
- clean commitに対するHATEの実行証跡を使用する。失敗・未実行・重複・異なるcommitの結果は拒否する。
- 全体の行・文・関数・分岐90%、ファイル別の行90%・分岐85%、変更行90%の既存基準を維持する。
- 手動は実行前の `docs/manual-bb/final-plan.json` とケース・モデルのハッシュに結び付ける。エージェントが通常ビルドを画面操作し、実際の観測を保存する。APIによる前提データ準備と、手動の観測を区別する。
- manual-bb standard gateとQEG standard gateを実行する。全DQルールを適用し、実行証跡を必須とする。
- 同じbuild/revision/environmentの72時間以内の証跡だけを採用する。失敗を過去の成功へ置き換えない。
- QEGへの変換はnative_graph契約を明示し、正規化前の各ツール出力も保存する。HATEの独自グラフをQEG正規グラフとして扱わない。
- HATEのテストはsuite単位で集約する。個別テストへ実測していない要件・コード被覆を割り当てない。
- 4件のP0リスクは保存・競合・承認・失効に関する設計上の回帰リスク。現行の自動・手動証跡で検証し、静的脆弱性が発見されたという意味にはしない。
- 他OS・他ブラウザ、外部デプロイ、未導入OSSの実運用は対象外。実データ・秘密情報・非公開リポジトリを検証資料に含めない。
